1. What it is

FileShare is a separate web application at files.company.com. It is not part of HyperAI or Teams. Employees sign in with their Microsoft account (single sign-on), the same company account they use for Teams and Outlook. They keep files and folders, share them with colleagues, save important files permanently after approval, and send files to outside people as a link or an email attachment after approval. HyperAI is not changed.

3. Users and sign-in

  • FileShare is a separate web application at files.company.com, reachable from the company network or VPN.
  • Users come from Microsoft 365 (Microsoft Entra ID), the same company accounts used for Teams and Outlook. A background job syncs them every 30 minutes, so nobody creates users by hand.
  • Single sign-on: "Sign in with Microsoft" (OpenID Connect). No separate password. MFA and company sign-in rules are applied by Microsoft.
  • Only employee accounts of the company's Microsoft tenant can use FileShare. Guest accounts are refused, even if they try to sign in. People disabled or removed in Microsoft lose access at the next sync.
  • New users get the role User. Colleagues for sharing and for the Roles page are picked from the synced user list.
  • Setup needed: one Entra ID app registration (sign-in, plus permission to read users, approved once by the Microsoft 365 admin).
  • How sync and sign-in work step by step: Technical tab, sections 2 and 3.

  • Every role change is logged with who changed it and when.

5. Approval

  1. The employee sends a request (send outside or save permanently) with a reason.
  2. Every Approver gets an email, except the sender. If no other Approver exists, Admins get it (again never the sender). The server always refuses a decision by the request's sender. If nobody else can approve, the request times out after 3 days.
  3. The email button opens the approval page in FileShare (signed in with Microsoft).
  4. Opening the email or page never approves. The approver checks the files (download), then clicks Approve or Reject (with reason).
  5. One approval is enough. The first decision wins; other approvers see "Already decided".
  6. No decision in 3 days: the request ends and the sender is told.

The page works only for the person it was sent to, only once, and only while that person still has the Approver or Admin role.

12. Security

  • Microsoft sign-in only; tokens checked against Entra ID; sessions in secure cookies.
  • Every check is done on the server for every request: owner, shared with, or approver of that request.
  • All files are sent as downloads (never shown in the browser).
  • Approval: page opening (GET) never decides; decision is a POST by the signed-in approver.
  • Link tokens are long random values stored only as hashes. 6-digit codes are stored with a server secret (HMAC), valid 5 minutes, with rate limits and lock-out.
  • Portal isolated in the DMZ with read-only access to the outbound bucket.
  • Activity log of uploads, shares, deletes, requests, decisions, role changes, codes and downloads.
  • Accepted risks: link and code use the same mailbox; attachments cannot be recalled; no malware scan in version 1.

2. Users: where they come from and how we sync them

Nobody is created in FileShare by hand. Users come from Microsoft Entra ID, the company directory behind Microsoft 365, Teams and Outlook. Every company employee account can use FileShare. Guest accounts cannot.

One-time setup in Entra ID (done by the Microsoft 365 admin)

  1. Register an app called "FileShare" with supported account types "Accounts in this organizational directory only (single tenant)". This gives a Tenant ID, a Client ID and a client secret (or certificate). Secrets expire (at most 2 years); put the renewal date in the IT calendar, otherwise sign-in and sync stop.
  2. Under Authentication, add platform "Web" (not "Single-page application") with redirect address https://files.company.com/auth/callback. It must be "Web" because our server, not the browser, exchanges the sign-in code using the secret.
  3. Permissions: openid, profile, email, User.Read (delegated, for sign-in) and User.Read.All (application, for the sync job and the sign-in check). The admin approves them once ("admin consent").
  4. Leave "Assignment required" off: every company account can use FileShare, and the sync lists every company user, so all of them must be able to sign in.
  5. The app server needs outbound HTTPS to login.microsoftonline.com and graph.microsoft.com (through the company proxy if one is used).

How the sync works (background job every 30 minutes)

  1. The job gets an app token from Microsoft (client credentials, scope https://graph.microsoft.com/.default, which means "the app permissions the admin approved", here User.Read.All) and calls Microsoft Graph:
    GET https://graph.microsoft.com/v1.0/users/delta?$select=id,displayName,mail,userPrincipalName,accountEnabled,userType,department
  2. The first run returns every user, page by page, and at the end a deltaLink. We save the deltaLink in the sync_state table.
  3. Every next run calls the saved deltaLink. Microsoft returns only people who were added, changed or removed since the last run, plus a new deltaLink.
  4. Each person is inserted or updated in users, matched by the Microsoft id (entra_id): name, email (mail, or userPrincipalName if mail is empty), department, active = accountEnabled, and last_seen_at = start time of this run.
  5. People removed or disabled in Microsoft are set to inactive: they cannot sign in, their sessions are deleted, and they disappear from the share picker and from approver lists. Their files follow the normal rules (temporary files still expire; permanent files stay and are never deleted).
  6. Guest accounts (userType = Guest) are never added. If an existing user is changed to Guest, they are set to inactive.
  7. A saved deltaLink works for up to 7 days. If it has expired (Microsoft answers with an error such as syncStateNotFound) or Microsoft answers 410 Gone, the job throws the deltaLink away and runs a full sync. A full sync lists only people who exist now, so people deleted in the meantime are not reported as removed. Therefore, after a full sync, every active user whose last_seen_at is older than this run is set to inactive and their sessions are deleted. The new deltaLink is saved only after this clean-up, so if the job fails half-way the next run repeats the full sync.
// simplified sync job
const runStart = new Date();
let full = !syncState.deltaLink;
let url = syncState.deltaLink ?? FIRST_DELTA_URL;
let newDeltaLink;
while (url) {
  let page;
  try {
    page = await graph.get(url);                    // app token, retries on 429/5xx
  } catch (e) {
    if (e.status === 410 || e.code === 'syncStateNotFound') {
      await syncState.clear(); full = true; url = FIRST_DELTA_URL; continue;
    }
    throw e;
  }
  for (const u of page.value) {
    if (u['@removed'])          { await users.deactivate(u.id); continue; }
    if (u.userType === 'Guest') { await users.deactivate(u.id); continue; }
    await users.upsert({ entraId: u.id, name: u.displayName,
      email: (u.mail ?? u.userPrincipalName).toLowerCase(),
      department: u.department, active: u.accountEnabled !== false,
      lastSeenAt: runStart });
  }
  url = page['@odata.nextLink'];
  if (page['@odata.deltaLink']) newDeltaLink = page['@odata.deltaLink'];
}
if (full) await users.deactivateNotSeenSince(runStart);   // people deleted while we were not syncing
await syncState.save(newDeltaLink);                        // saved last: if anything failed, the next run repeats the full sync

Why sync, if people sign in with Microsoft anyway? The share picker and the Roles page must list colleagues who have never opened FileShare, and someone who leaves the company must lose access within 30 minutes, even with an open session.

Safety net: if a person signs in before the sync has picked them up, the server looks them up once in Microsoft Graph by their Microsoft id (GET https://graph.microsoft.com/v1.0/users/{oid}?$select=id,displayName,mail,userPrincipalName,accountEnabled,userType,department, same app permission as the sync). They are added only if userType is Member and the account is enabled; otherwise sign-in is refused with "FileShare is for company employees only". This check is needed because guests invited into our Microsoft tenant can also sign in, and the token checks alone do not stop them. Name and email always come from Microsoft Graph, never from the email inside the sign-in token (Microsoft says that value can change and must not be used to decide access).

3. Sign-in (single sign-on)

  1. The user opens any FileShare page (for example an approval link /approve/...). Without a session, the server makes three random values: state, nonce and the PKCE code_verifier. It keeps them, together with the page the user wanted (only a relative path on our own site), in a 10-minute cookie __Host-fs_auth (HttpOnly, Secure, SameSite=Lax). It then redirects the browser to Microsoft's sign-in page https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/authorize (OpenID Connect authorization code flow with PKCE, scopes openid profile email User.Read, response_mode=query so Microsoft comes back with a normal GET). The server reads Microsoft's addresses and signing keys from https://login.microsoftonline.com/<tenant-id>/v2.0/.well-known/openid-configuration.
  2. Microsoft signs the user in, including MFA and company rules. Usually there is no prompt because they are already signed in to Microsoft 365.
  3. Microsoft sends the browser back to /auth/callback?code=...&state=.... The server checks that state matches the cookie, exchanges the code (with the code_verifier and the client secret) for an ID token, and checks the token: signed by Microsoft, iss = https://login.microsoftonline.com/<tenant-id>/v2.0, aud = our Client ID, tid = our tenant, nonce = the nonce in the cookie, not expired. openid-client checks state, iss, aud, nonce and expiry; we turn on its signature check with enableNonRepudiationChecks (off by default because the token comes straight from Microsoft over HTTPS), and our own code checks tid. Then it deletes __Host-fs_auth.
  4. The server finds the user by oid (= entra_id). Inactive users are refused. Unknown users go through the safety-net check in section 2.
  5. The server creates a session: a random 256-bit id, stored only as a hash in sessions, sent as cookie __Host-fs_session (HttpOnly, Secure, SameSite=Lax, Path=/, no Domain), valid 8 hours. The __Host- prefix means no other company.com website (for example share.company.com) can set or replace this cookie. The user is then sent to the page they wanted, so an approver who clicked an email link lands on the approval page.
  6. Every API call reads the cookie, loads the session and the user, and checks the user is still active.

The browser never holds Microsoft tokens; the server keeps everything (the "backend for frontend" pattern). FileShare never stores passwords. The first Admin is given in configuration by their Microsoft object id (FIRST_ADMIN_ENTRA_ID), matched to users.entra_id, never by email.

4. Database

Why PostgreSQL

  • Free, open source, very reliable, and already known to the team (HyperAI uses it). FileShare gets its own database, separate from HyperAI's.
  • Transactions: several changes succeed or fail together (for example "approve request" and "create link").
  • Conditional updates: UPDATE requests SET state='approved' WHERE id=$1 AND state='pending' makes sure only the first approver wins.
  • Arrays and good indexes, used for the folder path (path_ids).
  • Views and column-level permissions, used to give the DMZ portal only the few columns it needs.
  • Also holds the background job queue (pg-boss), so there is one less server to run.

How we create the database and tables

  1. Once, by the DBA: three logins and the database. The owner login only runs migrations; the running app and the portal get only the rights they need. 
    CREATE ROLE fileshare_owner  LOGIN PASSWORD '********';   -- owns the tables, used only for migrations at deploy
CREATE ROLE fileshare_app    LOGIN PASSWORD '********';   -- the running FileShare app
CREATE ROLE fileshare_portal LOGIN PASSWORD '********';   -- the DMZ portal
CREATE DATABASE fileshare OWNER fileshare_owner;
REVOKE ALL ON DATABASE fileshare FROM PUBLIC;
GRANT CONNECT ON DATABASE fileshare TO fileshare_app, fileshare_portal;
\c fileshare
CREATE SCHEMA pgboss AUTHORIZATION fileshare_app;          -- job queue, managed by pg-boss
    In PostgreSQL 15 and later the public schema belongs to the database owner, so the owner login can create the tables (and Drizzle's own drizzle migrations schema) without extra grants. The app starts pg-boss with createSchema: false (new PgBoss({ connectionString, schema: 'pgboss', createSchema: false })), because the schema already exists and the app login may not create schemas; pg-boss then creates its own tables inside pgboss.
  2. Tables are written in TypeScript with Drizzle (packages/db/schema.ts), for example: 
    export const items = pgTable('items', {
  id:        uuid('id').primaryKey().defaultRandom(),
  type:      text('type').notNull(),                  // 'file' | 'folder'
  ownerId:   uuid('owner_id').notNull().references(() => users.id),
  parentId:  uuid('parent_id'),                       // null = top of My files
  pathIds:   uuid('path_ids').array().notNull(),      // all parent folder ids
  name:      text('name').notNull(),
  size:      bigint('size', { mode: 'number' }),
  bucket:    text('bucket'),                          // temp-files | permanent-files (files only)
  objectKey: text('object_key'),                      // random id in MinIO (files only)
  retention: text('retention'),                       // 'temp' | 'hold' | 'permanent' (files only)
  expiresAt: timestamp('expires_at', { withTimezone: true }),   // temp files only
  createdAt: timestamp('created_at', { withTimezone: true }).defaultNow(),
});

// shares and request_files point to items:
//   shares.item_id        → items.id  ON DELETE CASCADE   (share disappears with the item)
//   request_files.item_id → items.id  ON DELETE SET NULL  (history keeps name and size)
  3. drizzle-kit generate turns each change into a numbered SQL migration file. Migration files are committed to Git and reviewed like code.
  4. On every deploy, pending migrations run with the fileshare_owner login (drizzle-kit migrate) before the app starts. The app itself runs with fileshare_app. Nobody changes the database by hand.
  5. A migration gives each login only what it needs: 
    -- running app: normal read/write, but the activity log is append only
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO fileshare_app;
REVOKE UPDATE, DELETE ON activity_log FROM fileshare_app;

5. File storage (blob storage) and MinIO

What blob storage is

"Blob" means binary large object: a file stored as an object with a key (its name) inside a bucket (a top-level container). The database only keeps information about each file (name, owner, size, bucket, key). The file bytes live in blob storage.

Why not keep files in the database?

  • Files make databases huge and slow, and backups very heavy.
  • Blob storage streams large files efficiently.
  • Blob storage has the features we need built in: locking files so they cannot be deleted, automatic deletion rules, and copying to a second server.

Why MinIO

  • Runs on our own server: files stay inside the company and there is no cloud bill.
  • Speaks the S3 API, the most common storage API. Our code uses the standard AWS SDK, so moving later to AWS S3 or another S3-compatible store is a configuration change.
  • Has what we need: Object Lock with default retention (permanent files), lifecycle rules (safety auto-delete), versioning, separate access keys per program with permission policies, and a second copy on another server (see the edition note below).
  • Alternatives considered: Azure Blob Storage (cloud, different SDK, files leave our servers); a plain file server or NFS share (no locking, no auto-delete rules, no per-program keys).
  • Edition note (checked October 2026): the old free open-source MinIO (community edition, AGPL) is no longer maintained — its GitHub project was archived in April 2026 and it gets no security fixes — so we do not use it. We use MinIO AIStor, which has the same S3 API and the same mc commands, so our code does not change. Its free edition, AIStor Free, costs nothing but needs a free licence file from min.io, runs on one server only, is not open source, and does not include replication. In the Review step we choose how permanent files get their second copy: a paid AIStor edition with replication, or AIStor Free plus a nightly copy to a second server (both shown below).

Setup (one script, kept in Git, run once)

mc alias set fs https://minio.internal:9000 ADMIN_KEY ADMIN_SECRET

      "Resource": ["arn:aws:s3:::temp-files/*","arn:aws:s3:::outbound/*"] },
    { "Effect": "Allow", "Action": ["s3:GetObject","s3:PutObject"],

The app has no delete, no lock bypass and no retention or lifecycle rights on permanent-files. ListBucket is there only so that "does this file exist?" checks answer "not found" correctly. Only the storage admin account can remove a lock, and only through a written IT procedure.

How the code uses it

  • AWS SDK v3 (@aws-sdk/client-s3) pointed at MinIO (endpoint + forcePathStyle: true).
  • Upload: @aws-sdk/lib-storage Upload streams the browser's upload straight into MinIO in parts; the file is never fully held in memory.
  • Key: a random id (crypto.randomUUID()). The real file name is only in the database, so storage reveals nothing.
  • Download: GetObject stream piped to the browser with Content-Disposition: attachment.
  • Copy: CopyObject inside MinIO (to permanent-files, or a package to outbound); the bytes never pass through the app.
  • Delete: DeleteObject (only in temp-files and outbound).
  • Buckets are private. There are no public URLs. Access keys exist only on the servers.

6. How temporary and permanent files are kept

retentionBucketexpires_atMeaning
temptemp-filesupload time + 7 daysNormal file, deleted after 7 days
holdtemp-filesunchangedPermanent save is waiting for approval; not deleted
permanentpermanent-filesemptyApproved; never deleted; locked in MinIO
empty (folders)—emptyFolders are only database rows and never expire
  1. Storage limit (10 GB per person): before each upload the API adds up the person's files: SELECT coalesce(sum(size),0) FROM items WHERE owner_id = $user AND type = 'file'. If that plus the new file is over 10 GB, the upload is refused with "Storage full". Temporary and permanent files both count; a temporary file stops counting once it is deleted.
  2. Upload: file goes to temp-files; row saved with retention='temp' and expires_at = now + 7 days.
  3. Clean-up job (every hour): finds expired temporary files, deletes the object in MinIO, then the row (its shares go with it; request_files keeps name and size), and writes the activity log. Unlike the owner's Delete, it does not cancel pending send requests or stop links, because each send request has its own frozen package. 
    SELECT id, object_key FROM items
WHERE type = 'file' AND retention = 'temp' AND expires_at < now()
LIMIT 500;
  4. Save permanently requested: retention='hold', so the clean-up job skips it while the approver decides.
  5. Approved: the job first asks MinIO (HeadObject) whether the file is already in permanent-files; if not, it copies it there under the same key (it is locked automatically) → updates the row (bucket='permanent-files', retention='permanent', expires_at = null) → deletes the temp copy. This order means a crash can never lose the file, and a retry never makes a second locked copy that could never be removed.
  6. Rejected or no decision in 3 days: back to retention='temp'. If its 7 days have already passed, expires_at = now + 24 hours and the owner is emailed; such a file cannot be sent for permanent save again (the API refuses it). So a file stays in temp-files at most 7 days + 3 days + 24 hours = 11 days, below the 14-day MinIO rule.
  7. Safety nets: every download checks expires_at again; if the clean-up job stops working, the MinIO 14-day rule still removes old temporary files.

Why a permanent file cannot be deleted: the page hides Delete; the API refuses (retention='permanent', or a folder that contains a permanent file); and MinIO refuses because the app's storage key has no delete permission on permanent-files, even if someone used that key directly. Object Lock is the last layer: the locked file version itself cannot be removed without the storage admin account. A plain delete by any other account would only add a "delete marker" that hides the file; the locked version stays and can be brought back.

7. How we know who owns a file and who can open it

  • items.owner_id is the person who uploaded the file. Only owners add to their own folders, so everything in a person's tree is theirs.
  • items.path_ids lists all parent folders. Example: a file in Projects › Q3 has path_ids = [Projects, Q3]. It is set when the item is created and never changes (there is no move).
  • shares has one row per item shared with a colleague. Sharing a folder covers everything whose path_ids contains that folder, including files added later, with no extra rows.
WhoCan
OwnerEverything on their own items
Colleague with a share (direct or through a parent folder)Download only

The check the server runs before every download from My files:

SELECT EXISTS (
  SELECT 1 FROM items i
  WHERE i.id = $item
    AND (i.type = 'folder' OR i.retention <> 'temp' OR i.expires_at > now())
    AND (
          i.owner_id = $user
       OR EXISTS (SELECT 1 FROM shares s
                  WHERE s.user_id = $user
                    AND (s.item_id = i.id OR s.item_id = ANY(i.path_ids)))
    )
) AS allowed;

Approvers do not get access to the files in My files. The approval page downloads through GET /api/requests/:id/download: for a send request it serves the request's frozen package; for a permanent-save request it serves the held files (a zip if there are several). The server allows it only when:

SELECT EXISTS (
  SELECT 1 FROM requests r
  JOIN approval_tokens t ON t.request_id = r.id
  JOIN users u           ON u.id = t.approver_id
  WHERE r.id = $request AND r.state = 'pending'
    AND t.approver_id = $user AND t.expires_at > now() AND t.used_at IS NULL
    AND u.active AND u.role IN ('approver','admin')
    AND r.sender_id <> $user
) AS allowed;
  • Top of My files = my items with no parent + items shared directly with me (shown as "Shared by …").
  • Inside a shared folder = that folder's children, allowed through path_ids.
  • The page hides buttons a person may not use, but the server checks every call. The browser is never trusted.

9. Backend (API) and portal

  • Every API call follows the same order: session check → input check (zod) → access check (section 7) → action → activity log.
  • Modules: auth, user-sync, items (folders, upload, download, delete, search), shares, requests (send outside, permanent save), approvals, roles, email, jobs.
  • Background jobs (pg-boss): user sync (every 30 minutes), clean-up (hourly), request timeout (hourly), build package (when Send is clicked), send email (with retries; every minute it also reads new portal events from the activity log, such as first download or a disabled link, and emails the sender).
  • Packages: when the employee clicks Send, the API first checks the total size: over 100 MB is refused, and over 20 MB only Link is allowed. A job then builds the package: a single file is copied as it is; folders and several files are streamed with archiver into one zip. The package is saved in temp-files as packages/<request id> — the portal cannot read this bucket — and its download name (for example contract.pdf or Projects.zip) is saved in requests.package_name. The job checks the real size again before approvers are emailed; if it is over the limit for the chosen method, the request ends and the sender is told. After approval: for Link, the app copies the package into outbound, sets access_until = approval time + the days the approver chose, then deletes the copy in temp-files; for Email attachment, the email job attaches the package and deletes it only after the email server has accepted the email, so retries still find it. After a rejection, a timeout or a cancellation, the package is deleted at once. When access_until passes, the clean-up job deletes the package from outbound. So outbound only ever holds approved link packages, and the MinIO 8-day safety rule counts from the copy made at approval, so a 7-day link is never cut short. Folder downloads in My files stream a zip straight to the browser.
  • Delete (by the owner): first the API refuses if the item is a permanent file, or a folder that contains any permanent file (same rule as the ⋮ menu). Then, in one transaction, delete the item and, for a folder, every item whose path_ids contains it. Their shares rows go with them (cascade); request_files.item_id becomes empty but name and size stay for history. Pending requests that contain these files are cancelled and the sender is told. Every link whose request contains a deleted file is set to disabled, and its package in outbound is deleted. The objects in temp-files are deleted after the transaction. The automatic 7-day clean-up does not stop links: the outside person has an approved frozen copy until the link time ends.
  • Approval decision: the approve or reject POST checks that the token belongs to the signed-in user, that the user still has the Approver or Admin role, that the user is not the request's sender, and that the request is still pending (conditional update). Other approvers' tokens then stop working.
  • Email: nodemailer through the company SMTP relay. For "Email attachment", the job attaches the package only after approval (its size was already checked when Send was clicked). A 20 MB file makes an email of about 27 MB (email encoding adds about one third), so the company relay must accept messages of at least 30 MB from files@company.com; some outside mail servers may still refuse it.
  • Portal: a separate small Fastify program with its own database login and storage key, plain HTML pages and four routes: GET /s/:token shows the page and sends nothing · POST /s/:token/code sends a code · POST /s/:token/verify checks the code · GET /s/:token/download sends the package (the file or the zip) with its download name. After a correct code, the portal creates a random download key valid for 30 minutes, stores only its hash and expiry in the codes row (download_hash, download_until) and gives the browser the cookie __Host-fs_dl (HttpOnly, Secure, SameSite=Strict). Download needs both the link token and this cookie, and checks again that the link is not disabled and access_until has not passed. The portal reads only the portal_links view; for "first download" and "link disabled" it writes an activity-log row, and the app's email job does the emailing.
